AI, Code & Trust

Let's be totally honest about AI. Here is where it fails, why we still use it to type fast, and how we actually keep Miqu memory-safe and private.

Genuine, Documented Issues with LLM Coding

Hidden Vulnerabilities

LLMs frequently generate plausible-looking code that omits basic input validation or memory-safety checks, introducing subtle bugs like integer overflows, off-by-one errors, and deprecated cryptographic suites.

Hallucinated Dependencies

Models occasionally fabricate package names and function signatures. Attackers actively register these hallucinated package names on public registries to inject malicious code directly into automated build pipelines.

Flow Disruption

Meticulously verifying confident but subtly flawed code often takes more time than authoring it from scratch. This forces engineers into a passive reviewer/auditor role, breaking the deep focus of active programming.

Licensing & Data Leaks

Models regularly output verbatim memorized code without attribution, risking unintended GPL or MIT license violations. They can also surface configuration tokens and private identifiers embedded in public training datasets.

Skill Degradation

Excessive reliance on AI deprives developers of the iterative problem-solving and debugging struggles needed to build deep first-principles intuition, reducing their ability to critically evaluate software.

Data Starvation

Widespread AI adoption has caused a noticeable drop in organic questions on public developer forums. This deprives future models of fresh human knowledge, raising the risk of recursive model collapse.

Minimal Viable Implementation

When asked for a high-level outcome (e.g., displaying "Hello World"), models may architect middle-layer classes like a TextView widget. Because the user never specified requirements for that intermediate layer, the model may implement only the bare minimum needed for the prompt—leaving the abstraction half-done and missing core features like multiline wrapping.

God Classes & Redundant Reinvention

Lacking repository-wide awareness, models frequently dump all responsibilities into giant monolithic classes ("God Objects"), or author completely separate, parallel classes with redundant boilerplate instead of properly extending or composing with existing abstractions.

Code Churn & Cascading Rewrites

When structural flaws surface in AI-generated systems, surgical refactoring is often unfeasible due to opaque interdependencies. Instead of incrementally fixing the foundation, developers are pushed into a total bottom-to-top overhaul, causing extreme code churn where codebases are repeatedly rewritten rather than steadily evolved.

Weighing the Criticisms of AI Code Generation

The Historical Precedent

Every evolution in tooling was once attacked as "not real programming." Assembly programmers claimed high-level compilers produced lazy bloat; later critics attacked IDE autocompletion and Stack Overflow. Theoretical purism always concedes to pragmatic leverage.

The Purity Trap

Purists confuse keystrokes with engineering. Typing syntax by hand is manual labor; engineering is defining architecture, memory boundaries, and state machines. Discrediting software merely because an accelerator typed the boilerplate is gatekeeping, not craftsmanship.

If Boilerplate Is Not the Issue, What Is Its Extent?

Critics often concede that using AI for "mere boilerplate" is acceptable. But where does boilerplate end? When an IDE scaffolds a complex Android Activity with lifecycles and navigation, it is celebrated as productivity. Even beloved human-crafted compositors like Hyprland openly began by borrowing configuration parsing and event loop boilerplate from wlroots' reference implementation, tinywl. When a human copies reference boilerplate to build something greater, the community calls it pragmatic engineering.

Why then is the exact same foundation delegitimized when an accelerator types the syntax? If taking tinywl's loops as boilerplate is valid, then prompting an LLM to scaffold Wayland dispatch loops is functionally identical. The boundary between "engineering" and "boilerplate" is entirely arbitrary.

Big Tech's Black Boxes

Proprietary software giants openly write 50%+ of their code with AI, shielded behind closed-source binaries without public scrutiny. Open-source builders use the exact same accelerators but face performative outrage simply because their git history is transparent.

The Open-Source Irony

Major ecosystems, including the Linux kernel, routinely merge machine-assisted patches as long as they survive human review and strict test suites. The loudest critics demanding "pure hand-typed" code are actively relying on software built with machine assistance.

The "Clean Code" Double Standard

Human-written code has always been famously messy, held together by the age-old rule: "If it works, don't touch it." Multi-million-dollar cult games and foundational tools have shipped on giant ladders of nested if statements and duct-taped scripts without outcry. Yet critics hold AI code to a superhuman purity test—demanding textbook design patterns and pristine refactorability that most production human code never met in the first place.

The Omarchy Paradox: Upstream Gravity & AI Velocity

Omarchy is flying high on the shoulders of Hyprland, driven by the frantic velocity of agentic scripting and vibecoded automation. But downstream layers moving at AI speed will inevitably outpace their native C++ foundations. As downstream users demand faster IPC turnaround and custom compositor hooks, Hyprland may soon be perceived as the bottleneck holding the ecosystem back.

Through community hype and financial donation backing, downstream AI ecosystems exert subconscious gravitational pull on upstream maintainers. Even if creators pledge independence, the velocity disparity will continuously pressure foundational C++ projects to match that pace—raising the question of how long human-only craftsmanship can resist the very AI acceleration fueling its popularity.

The Calculator Dilemma: Purity vs. Sovereignty

Which would you prefer: an AI-assisted offline calculator, or a closed-source Big Tech calculator that phones home and connects to the internet? An artisanal, human-written offline tool is ideal in theory—but what if its design clashes with your desktop, fails to sync with your system theme, or lacks modern Wayland ergonomics? When off-the-shelf software doesn't fit your environment, using AI to curate a lightweight, 100% offline utility tailored precisely to your own system is the most pragmatic, privacy-respecting choice available.

The Architecture Dilemma: Shipped Scaffolding vs. Obsolete Perfection

Software engineering has always wrestled with two opposing methodologies. The first is evolutionary scaffolding: author a workable baseline quickly, stack features upwards, and refactor downward only when higher layers buckle. It delivers tangible results immediately, but risks brittle seams and cascading overhauls. The second is foundational purism: refuse to build higher layers until the lower foundation is mathematically pristine. It promises textbook elegance, but demands clairvoyance about unknown future requirements, moves at a crawl, and frequently succumbs to developer burnout or obsolescence before the software ever ships.

With AI acceleration, the first approach has surged in popularity, enabling solo creators to flood ecosystems with visually stunning, highly functional software in months rather than decades. Purists dismiss this wave as fragile scaffolding built on sand. Yet Gall's Law and engineering history remind us of an uncomfortable truth: an imperfect system that actually ships and adapts in the wild will always outlive a theoretically flawless architecture that was abandoned before its first release.

The Cybersecurity Dilemma: Machine-Speed Threats vs. Human Latency

Avoiding AI has become like avoiding the smartphone: an individual may choose not to use it, but the banking networks, cloud servers, and public infrastructure they depend on already do. For decades, human-written code has harbored dormant zero-days—from OpenSSL to recent PHP argument injections—that evaded manual audits for years. Today, LLMs and automated agents can parse millions of lines of code to uncover subtle edge-case loopholes at machine speed. Because malicious actors operate without ethical hesitation, choosing not to use AI for defensive auditing simply guarantees that an attacker will find your vulnerabilities before you do.

This forces an urgent operational reality: when a critical zero-day is actively weaponized against production infrastructure, a manual human patch may take weeks of surgical deliberation while servers remain defenseless. You cannot take down global financial systems or hospital infrastructure for a month to wait for artisanal code. While an AI-generated patch carries the risk of introducing secondary bugs, the alternative—letting active exploits run rampant while rejecting machine assistance out of purist dogma—is untenable. In an asymmetric threat environment, machine-speed defense is no longer optional.

The DHH Shift: Enthusiasm, Efficiency & The Reality Gap

Recently, veteran creator David Heinemeier Hansson (DHH) voiced enthusiastic praise for the latest generation of coding agents, noting that while he would not have "vibecoded" a year ago, he does so now because AI has become remarkably efficient. His perspective validates the undeniable technological leap: coding models have evolved from clumsy autocomplete toys into formidable accelerators capable of scaffolded execution.

Yet declaring AI "extremely efficient" is inherently subjective. If models were truly self-sufficient or near-flawless, AI laboratories would not be frantically releasing weekly architectural revisions to patch basic reasoning deficits and hallucination traps. A significant reality gap remains. AI will likely never achieve mythical human-level perfection—but then again, human coders have never been perfect either. The sensible path is neither uncritical hype nor stubborn dismissal; it is harnessing AI's undeniable velocity while enforcing rigorous multi-model auditing, human skepticism, and careful architectural pacing.

Who Is a Developer?

Where Does the Boundary Lie?

How much abstraction is allowed before someone stops being a developer? Where is the line actually drawn? Does it require writing raw C code against kernel syscalls? Is it authoring the window manager from scratch? Or does scripting an installer that downloads prebuilt compositors, status bars, and widgets—and stitches them all together—still count?

Every developer stands on someone else's abstraction. The question is: where does using tools end, and building software begin?

The "Rice in an ISO" Paradox

Consider a familiar scenario: someone takes Arch Linux as an OS base, Hyprland as compositor boilerplate, Quickshell as shell boilerplate, a community riced config as UI boilerplate, and packages it all into an ISO. Are they a software developer, a desktop environment creator, or a distribution maintainer?

If assembling layers of existing binaries and riced configurations into an installer is celebrated as building an OS or desktop, why should engineering native C++20 daemons and custom Wayland protocols be questioned simply because an LLM assisted with boilerplate?

When boilerplate is layered on top of boilerplate, who decides which layer confers the title of "developer"?

How to Criticize This Project: An Honest Steelman

Here is the strongest, most honest case critics make against Miqu:

A Vibecoded Hyprland Clone

Hyprland was built by hand over years of hard C++ engineering. Miqu borrowed its look, tiling ideas, and layout, using AI to generate code fast. It is an unoriginal, machine-generated copy riding on someone else's work.

Imperfect Edge Cases

AI writes code that works on simple cases but fails on subtle bugs. Miqu likely has broken protocol handlers, glitchy multi-monitor quirks, and half-done parts that have never been battle-tested for daily use.

Too Broad, Not Deep Enough

Instead of polishing one compositor, Miqu built a window manager, a UI toolkit, 14 desktop apps, and Android companions. It spreads itself too thin before the core foundation is even mature.

Relying on Upstream Libraries

Hyprland built its own backend and renderer (Aquamarine). Miqu relies on stock wlroots and scenefx. If upstream libraries change direction or drop features, Miqu is stuck.

Our Response: Inspiration, Divergence & How We Keep It Safe

We openly credit Hyprland as our primary inspiration: its Wayland base, fluid tiling, and desktop feel inspired Miqu. But we did not just copy it—we diverged in several core ways:

Notable Differences
Backend Hyprland: Custom Aquamarine Miqu: Upstream wlroots
Renderer Hyprland: Custom renderer Miqu: scenefx
Config Model Hyprland: Auto-creates ~/.config Miqu: Zero-config baseline & --init-config
UI Toolkit Hyprland: Bundled system-wide Miqu: Standalone miqutoolkit
Scope Hyprland: Core desktop daemons Miqu: 14 Linux apps + companion Android
Other Features Decoupled theming via 'source =' Strict 0.0% idle CPU event loops
How We Keep It Safe

These criticisms are valid. That is why we use strict engineering rules to catch AI mistakes and keep Miqu stable, safe, and private:

Strict C++20 RAII

AI often writes memory leaks. We ban raw owning pointers. Every resource is scope-bound and cleans itself up automatically.

Zero-Warning Builds

We compile with -Wall -Werror. A single compiler warning breaks the build. AddressSanitizer catches memory bugs automatically.

0.0% Idle CPU

AI loves polling loops. We ban them. When nothing is happening on screen, Miqu sleeps at exactly 0.0% CPU in the Wayland event loop.

Standard Protocols

We don't invent hacky workarounds. We follow standard Wayland and scenefx protocol interfaces directly.

Multi-LLM & Human Audits

Code is checked regularly by multiple AI models cross-checking each other alongside human review to catch blind spots early.

Ripple-Effect Tracing

We never patch blindly. Both human and AI trace how changes affect the compositor, toolkit, and apps before merging.

100% Offline

Zero telemetry. Zero tracking. The code links to no network libraries and runs entirely on your local machine.

100% Open Source

Miqu is licensed under MIT. Every line of code is open for anyone to inspect, audit, or challenge.

Careful Pacing & Pruning

We move slowly and carefully. If a feature adds too much complexity or risks stability, we drop it. Simple and reliable wins.

Miqu is an open experiment by a solo developer exploring how far modern AI tools and strict engineering discipline can go in building a complete desktop. It is actively improving, hardened by strict rules, and built completely in public for anyone to test or improve.
