Ecosystem Guide & Architecture

Documentation

Welcome to Miqu. This guide walks you through how Miqu is designed, how configuration works, how components communicate, and how to build and extend the desktop environment.

Overview & Platform Base

Our goal with Miqu is simple: build a complete, cohesive, and modern Wayland desktop environment from the ground up. Instead of gluing together disparate tools with conflicting styles and heavy background services, Miqu gives you a unified ecosystem where every application shares the exact same design language, configuration model, and lightweight performance philosophy.

We develop and test Miqu primarily on Arch Linux. Because everything is built on open Wayland standards via wlroots, Cairo, and Pango, the entire desktop compiles and runs cleanly across other modern Linux distributions without vendor lock-in.

“A fully functional desktop environment is our goal, and we make steady progress by adhering to clean code, clear boundaries, and zero hidden magic.”

How Configuration Works

Configuration management can easily become messy if not carefully planned. Many desktops scatter settings across hidden databases, layered overrides, or opaque background daemons. In Miqu, we follow a straightforward two-tier model that keeps your configuration predictable, safe, and completely transparent.

1. Zero-Config Out of the Box

When you install Miqu, every application works immediately out of the box. Applications read directly from authoritative system defaults in /usr/share/<app>/<app>.conf. We never pollute your home directory or auto-create files in ~/.config/ until you explicitly ask for them.

2. On-Demand Initialization with Safe Archiving

Whenever you are ready to customize an application, simply run: 

<app-name> --init-config

This writes a fresh, fully documented configuration template to ~/.config/<app>/<app>.conf. If you already have an existing configuration, it is never silently overwritten—it is safely backed up with a timestamp (.bak.YYYYMMDD-HHMMSS) before the new template is written.

3. Single-File Standalone Authority

Once your user configuration exists, the application reads only from that file. There is no silent fallback merging in C++ code where missing values secretly revert to hardcoded values. What you see in your configuration file is exactly what gets applied.

4. Decoupled Dynamic Theming

Dynamic theming is completely decoupled from our C++ UI toolkit. If you want dynamic color palettes generated from your wallpaper via miqutheme, you include this line in your config: 

source = ~/.config/miqutheme/current/miqutoolkit.conf

Sourced files are automatically watched via inotify. Whenever your wallpaper or theme changes, all running apps reload colors live without needing a restart. If you prefer fixed, static colors, you can simply remove or comment out the source line and define colors directly.

Build System & Installation

Building software should never be a mystery. Every repository in Miqu includes a standardized ~20-line make.sh script so the workflow is identical across all components:

Building locally: Run ./make.sh as a normal user. It configures CMake and builds into a local build/ directory without touching your system.

Installing system-wide: Run sudo ./make.sh. It automatically compiles and installs binaries, assets, desktop entries, and icons directly to /usr.

One-command full ecosystem install: In the root workspace repository, running ./install_all.sh compiles and installs everything in correct topological order:

git clone --recurse-submodules https://github.com/miqu-project/miqu-project.git
cd miqu-project
./install_all.sh

Core Craftsmanship Standards

We adhere to strict engineering disciplines across our C++20 codebase to make sure the desktop remains stable, performant, and maintainable:

  • Small, single-responsibility functions: Functions stay around 40–50 lines. Geometry math, state validation, and rendering routines are broken into clear helpers rather than monolithic blocks.
  • Strict RAII and pointer safety: Raw allocations, file descriptors, Cairo contexts, and Pango layouts are immediately bound to RAII guards or std::unique_ptr. No resource leaks, no zombie states.
  • Zero idle CPU usage: Everything is event-driven. When there are no input events, damaged scene buffers, or running animations, the compositor and apps sleep completely in the Wayland event loop at 0.0% CPU.
  • Main-thread UI confinement: Wayland protocols and rendering run strictly on the main event-loop thread. Background worker threads communicate cleanly via pipes or eventfd rather than touching UI widgets directly.
  • Toolkit sovereignty: Client applications never bypass miqutoolkit to draw raw surfaces directly. When an app needs a new UI control, we build it directly inside the toolkit for everyone to use.

Active Ecosystem Roadmap

We are steadily evolving the Miqu desktop environment. Here is our active focus for upcoming releases:

  1. miquctl IPC CLI: First-party command-line controller communicating over a Unix domain socket for workspace switching, window dispatching, monitor configuration, and runtime diagnostics.
  2. Plugin System v2.0: An event bus for window and workspace lifecycle hooks, multi-finger gesture callbacks, and custom tiling layout engines (spiral, dwindle, monocle).
  3. Next Desktop Utilities: Screenshot tool (miqushot), blue light filter (miqusunset), centralized settings (miqusettings), and power dialog (miqupower).
  4. Native Toolkit Animations: First-class frame-driven physics, easing curves, and geometry interpolations built directly into miqutoolkit.
  5. Multi-Touch Gestures: Multi-finger gesture recognition for touchscreens and touchpads (swipes, pinch-to-zoom, edge gestures).
Code Integrity, Authorship & Engineering Safety

AI in Software & Code Safety

A rigorous examination of software authorship, abstraction layers, and the double standards of modern programming—followed by how Miqu strictly enforces memory safety, offline privacy, and complete open-source transparency.

Part 1 — Universal Principles

The Epistemology of Modern Software Authorship

A technology-wide perspective on abstractions, software tools, and the double standards of modern code criticism.

01

Is Using AI in Coding Inherently Flawed?

When developers discuss artificial intelligence in programming, a core question arises: If you use an AI tool to assist in writing code, are you still the author of your software?

To answer this objectively, we must understand how software has actually evolved over the past seventy years. Writing software has never been about the physical labor of pressing keys on a keyboard. It has always been about solving problems, structuring logic, managing trade-offs, and directing machines to perform deterministic tasks.

The History of Computing Is a History of Abstractions

In the earliest days of computing, programming required punching holes into paper cards or toggling front-panel switches in raw binary. Every single opcode had to be calculated by hand.

When assembly language and the first compilers were invented, critics argued that using a compiler was "cheating" and that future engineers would no longer understand the machine. Yet without compilers, modern operating systems, web browsers, and scientific computing would be impossible. Every major milestone in software history—from machine code to assembly, from C to C++, from manual memory tracking to standard libraries, garbage collectors, and high-level frameworks—is an abstraction that automates mechanical labor so human developers can tackle larger, more ambitious architectures.

The TextView Test: Nobody Codes to the Lowest Layer

Consider a modern example: an Android developer creating an application. To display a simple line of text, they instantiate a TextView.

Did that developer write the HarfBuzz font shaping engine? Did they write the FreeType glyph rasterizer, the Skia 2D rendering pipeline, the SurfaceFlinger compositor protocol, the Linux kernel framebuffers, or the GPU graphics drivers?

The Abstraction Reality: If using pre-existing code, libraries, and tools meant you were not an author, then almost no one alive today could be called a software developer. Unless you personally smelt the silicon, design the CPU instruction set, write the hardware drivers, and interact directly with hardware registers without any runtime library, you are always building upon someone else's work.

Assembling vs. Building: A Crucial Technical Distinction

There is a vital difference between assembling finished pieces and building components from the ground up:

Suppose someone downloads Arch Linux, installs Hyprland and Quickshell, configures dotfiles, adds a custom theme, and bundles the setup into a downloadable ISO. Are they the developer of that ISO?

They are the author and curator of that distribution ISO bundle. But they did not write Hyprland, the Wayland protocol bindings, or Quickshell. They orchestrated existing tools. In contrast, building the compositor itself, developing an independent UI toolkit, and programming native applications requires designing internal state machines, memory ownership, and low-level protocol lifecycles.

Where Is the Boundary Between an Assembler and a Developer?

This leads to a critical philosophical question: Where exactly is the boundary between a "developer" and an "assembler"?

If using an abstraction or automated assistance makes someone "just an assembler," then the purist argument immediately collapses into an infinite regress. Does a C++ engineer become an assembler because they use std::vector, libc, and an optimizing compiler? Does a Linux kernel maintainer become an assembler because they build on top of CPU microcode and hardware specifications they did not design?

Mere Orchestration (Assembly)

Taking finished, pre-compiled black-box applications and gluing them together using text configuration files, shell scripts, and themes. No new internal state machines, algorithms, or execution loops are authored.

System Creation (Development)

Designing new domain logic, data models, memory ownership lifecycles, and protocol state machines. Even when built upon lower-level primitives, the developer authors the logic that governs system behavior.

Using an AI assistant to accelerate typing boilerplate syntax does not turn a software engineer into an assembler—any more than using an IDE autocomplete or a compiler does. The developer remains the author because they define the system, govern its logic, and bear full technical accountability for its execution.

Code Convergence on Constrained Protocols: Similar Does Not Mean Copied

Another frequent misunderstanding is the phenomenon of code convergence. When developers write software against strict system protocols and graphics APIs, their code will often look remarkably similar to existing projects on GitHub.

Consider implementing dual-kawase background blur in a Wayland compositor using SceneFX or wlroots. The graphics pipeline dictates an exact sequence: bind the scene buffer, query the damaged bounding box, allocate offscreen framebuffers, dispatch shader passes with specific parameters (blur radius, iterations, noise), sample texture coordinates, and composite back to the screen.

The Merger Doctrine in Code: There are only one or two mathematically optimal ways to execute this pipeline. Whether written by a human or generated with the help of an AI, the code will naturally converge with other implementations across the open-source ecosystem. In computer science and copyright law, this is recognized as functional convergence: when a protocol allows only one optimal solution, similar code is the inevitable result of correct engineering, not plagiarism.

The Reality of AI Code: Context Loss and the “Half-Done” Trap

In the early days of generative AI, detecting machine-written code was trivial. Early models produced obvious patterns, hallucinated libraries, and repetitive boilerplate. Today, with modern reasoning models and agentic workflows, detecting AI-generated code has become virtually impossible. On basic or isolated problems, an AI can produce clean, idiomatic code that matches or even outperforms senior developers.

However, when applied to massive, multi-repository projects, AI hits a fundamental wall: it rapidly loses global context.

An AI model does not have the entire project architecture internalized. In a real-world desktop ecosystem with centralized theming, window management protocols, and custom UI components, asking an AI to simply “add an About Us window” will fail. The AI will rarely explore the codebase deeply enough to understand how global theming is implemented; instead, it will invent an ad-hoc layout with hardcoded colors and custom margins that completely breaks visual consistency. Even with comprehensive doctrine (such as an AGENTS.md file), LLM-powered IDEs frequently skip rules or lose focus unless actively guided by the developer on where to look and what contracts to enforce.

Furthermore, AI models suffer from a pervasive “minimum-viable” bias. If you prompt an AI to create a TextView widget, it will generate the absolute minimum code to draw a single line of text. It will routinely omit critical real-world requirements: multiline wrapping, text alignment, ellipsis truncation, bi-directional text, and DPI scaling. It delivers a superficial, “half-done” implementation that compiles but immediately fails in production.

The human developer must hold the mental map of every class, dependency, and design token in their head. The developer must anticipate missing edge cases, seal every functional gap in the prompt, direct the model's focus, and audit every line of output. When a developer performs this immense cognitive labor, criticizing them simply because they did not physically stroke the keys for repetitive builder syntax is completely futile.

02

What True Software Authorship Actually Means

Keystrokes are cheap. An AI model can generate thousands of lines of syntax in seconds, but it has no intent, no understanding of system constraints, no real-world experience, and no ability to test software on real hardware.

True authorship in software engineering consists of three non-delegable pillars:

PILLAR 1
Intent

Deciding what needs to be built, why it must exist, and what problem it solves for users.

PILLAR 2
Architecture

Designing data structures, component boundaries, memory ownership models, and lifecycle contracts.

PILLAR 3
Accountability

Auditing every line, verifying memory safety, testing on physical devices, and taking total responsibility for bugs.

“An architect designs the structural blueprint, load calculations, and safety exits of a building without pouring every bucket of concrete by hand. The human software engineer who directs, verifies, and debugs an AI-assisted codebase is that architect.”
03

The Double Standard of Closed-Source Software

There is a glaring contradiction in how AI-assisted software is judged across the tech industry today.

Big Tech Companies Extensively Rely on AI-Generated Code

Major proprietary tech companies now openly state that 25% to over 50% of their new internal codebase is written by artificial intelligence models. Their commercial products, cloud backends, and desktop operating systems are saturated with machine-generated code.

Yet their operating systems (such as Windows and macOS) and commercial apps remain 100% closed-source. Millions of users and businesses run this software every day without ever being allowed to view a single line of the source code.

Even the Linux Kernel Incorporates AI-Assisted Commits

This reality extends far beyond proprietary tech giants. Even inside the most scrutinized, mission-critical open-source project in human history—the Linux kernel itself—maintainers and corporate contributors from Intel, Google, Red Hat, and AMD actively use LLMs to write drivers, refactor subsystems, and draft patch commits.

As Linus Torvalds and senior kernel maintainers have pointed out, AI is simply an inevitable evolution in developer toolchains. The kernel community does not reject a patch because a modern tool assisted in writing it; they evaluate whether the code is correct, memory-safe, and rigorously tested.

The Reality Check: If the very kernel powering every Android smartphone, cloud datacenter, internet router, and Linux workstation contains LLM-assisted code, where exactly are critics planning to hide? What operating system, server, or digital device can they use that is completely free of machine-assisted software? The debate is no longer about whether AI tools are used; it is about whether the resulting software is open, auditable, and safe.

The Asymmetry of Scrutiny

Closed-source companies avoid public criticism simply because they hide their code behind binary blobs and legal agreements. You cannot inspect whether their AI-generated code has memory leaks, security backdoors, or telemetry scripts harvesting your personal files, keystrokes, and browsing habits.

In contrast, open-source developers who are completely honest and transparent about using AI tools often face intense scrutiny—even though their entire codebase is public, reproducible, and verifiable by anyone on the planet. This is a clear double standard.

The Universal Standard for Trusting Software

Code quality and security are not determined by whether a human finger physically tapped every key or whether an AI autocomplete suggested a loop. Security is determined by whether the software is provably constrained, memory-safe, completely auditable, and incapable of violating your privacy.

Part 2 — Miqu's Guarantees

How Miqu Meets Rigorous Engineering Standards

How our architecture, strict C++20 memory safety, offline privacy, and open-source practices fulfill these principles.

04

Real Engineering: Built from the Ground Up

Miqu is not an assembled configuration, a collection of dotfiles, or a reskinned Linux ISO. We engineered an entire Wayland desktop environment from scratch across 18 specialized repositories:

CORE COMPOSITOR
miquland

Native Wayland compositor written in C++20 on wlroots, handling output rendering, tiling/floating window management, layer-shell protocols, and IPC plugins.

SHARED UI TOOLKIT
miqutoolkit

Custom Cairo, Pango, and Wayland UI framework providing design tokens, layout containers, and live theme propagation across all applications.

DESKTOP SUITE
16 Native Apps

Standalone apps: status bar (miqubar), desktop canvas (miqudesk), firewall center (miqusecure), music player (miqumusic), launcher (miqulauncher), and lockscreen (miqulock).

We use AI as a rapid typing tool and syntax assistant. But every architectural contract, memory boundary, and Wayland event loop is designed, directed, and verified by human engineering.

Strict Memory Safety and Technical Discipline

Unconstrained AI-generated code is prone to memory leaks, dangling pointers, and undefined behavior. In Miqu, this is strictly prevented through non-negotiable technical rules:

Strict C++20 RAII

Raw owning pointers are prohibited. Every file descriptor, Wayland protocol surface, and Cairo context is wrapped in smart pointers or scope-bound RAII guards. Memory leaks are structurally impossible.

Zero Compiler Warnings

All code compiles under strict compiler flags (-Wall -Wextra -Werror). A single compiler warning is treated as a fatal build error and rejected.

Runtime Sanitizers

We run AddressSanitizer (ASan) and UndefinedBehaviorSanitizer (UBSan) to proactively catch buffer overflows, alignment faults, and hidden memory bugs before code reaches users.

0.0% Idle CPU Discipline

Miqu applications never spin in continuous polling loops. The stack is strictly event-driven; when there is no user input or screen damage, processes sleep completely in the event loop at 0.0% CPU.

05

Testing, Audits, and a Unified Architectural Rulebook

Maintaining 18 repositories with high reliability requires strict governance:

The AGENTS.md Single Rulebook

Every repository follows the identical architectural doctrine. This document enforces the uniform two-tier configuration model, zero source-code appearance defaults, strict thread isolation, and lifecycle safety. Both AI tools and human developers operate under these exact constraints.

Automated Static Analysis & Lifecycle Verification

Continuous automated tools inspect code for Wayland protocol lifecycle violations, iterator invalidation hazards, and resource leaks across all 18 repositories.

Main-Thread UI Confinement & Worker Isolation

Background tasks (MPD connections, system telemetry, socket I/O) are isolated to worker threads and communicate only through non-blocking event loops (eventfd, pipes)—never mutating UI widgets directly.

06

Our Two Non-Negotiable Guarantees

“You should never have to take a developer's word for security. True trust is built on two verifiable pillars: complete offline independence and fully public source code.”

Miqu delivers this trust through two structural guarantees:

1. 100% Offline Isolation (Zero Telemetry)

Miqu contains no tracking scripts, no telemetry pings, no analytics, and no background cloud connections. The compositor, toolkit, and desktop apps do not even link to network communication libraries. Miqu runs identically on a computer with no internet connection whatsoever. Your files, activity, and keystrokes never leave your machine.

2. 100% Open-Source Under the MIT License

Every single line of C++20, Wayland protocol bindings, and CMake build logic across all 18 repositories is publicly available on GitHub under the permissive MIT license. Anyone in the world can inspect the code, verify the build process, audit memory management, and run the software independently.
